### TA-233 — The capture cursor/reticle does not track the region actually being drawn

- **Phase:** 3
- **Priority:** P3
- **Suggested labels:** `capture`, `ux`, `multi-display`, `resolved`
- **Problem it solves:** During today's Block A pass (DSP-03, laptop @125%), the
  reporter marked up a quick-capture screenshot with two arrows: one pointing at
  where the capture target/reticle appeared to be, the other at where the
  highlighted selection rectangle was actually being drawn — the two do not
  coincide (`capture frame on laptop visible for quick cqpture.png`). The
  region capture itself still produced correct content (`region capture on
  laptop.png` reads `4LAPTOP 5LAPTOP 6LAPTOP 7LA...`, confirming the export is

  being misleading, not about what gets exported.

  bug.** The reticle and the highlighted rectangle are not disagreeing with
  each other - the highlight is one shared logical selection rectangle,

  physical pixels tall on each screen, which is what a hand-annotated
  screenshot comparing the two screens' pieces against each other reads as
  "the two do not coincide." The reticle itself was separately confirmed to
  track its own screen's actively-dragged corner smoothly, with no jump or
  lag. See the frame-by-frame measurement below for the numbers.

## HW-6 measured on real hardware, 2026-09-15 — reclassified: not a tracking bug, a DPI-scaling display artifact

**Context.** Recorded the boundary-crossing drag with OBS (two Display Capture
sources, one per physical monitor, composited side by side at native
resolution — laptop 1920x1080 physical @125% DPR, external 1920x1080
physical @100% DPR, seam at physical x=1920 in the recording). Measured
frame-by-frame with Pillow rather than eyeballed, per `WORKING_AGREEMENTS.md`.

Across 22 consecutive frames spanning a continuous 1.6s drag through the
boundary crossing, the two per-screen highlight pieces at the seam hold
these physical-pixel extents (stable, not a one-frame fluke):

| | top | bottom | height |
|---|---|---|---|
| Laptop piece (@125% DPR) | 529px | 837px | 308px |
| External piece (@100% DPR) | 423px | 669px | 246px |

Ratios: `529/423 = 1.2506`, `308/246 = 1.2520` — both within rounding of
**1.25, exactly the laptop's DPR relative to the external's**. Dividing each
piece's physical extent by its own screen's DPR recovers the *same* logical
top (`529/1.25=423.2` vs `423/1.0=423`) and the *same* logical height
(`308/1.25=246.4` vs `246/1.0=246`). This is not two independently-computed
rectangles disagreeing — it's one shared logical rectangle, rendered
correctly at each screen's own physical scale. A window, a button, or
Windows' own UI chrome would show the identical physical-size difference
between these two monitors; the highlight isn't doing anything they don't.

The reticle was checked against this too: the crosshair's y-position
tracked the *external* piece's own actively-dragged corner (within ~10px,
consistent with crosshair-vs-hotspot rounding) across all 24 sampled
frames, with x moving smoothly frame to frame (560px -> 847px over 1.6s,
no jumps). It only looks like it "disagrees with the highlight" if you
compare it against the *laptop* piece it is no longer over — which is
exactly the DPI-scaled size difference above, not a lag or a second bug.

**This reframes both TA-233 and TA-223's shared hypothesis.** The original
reports ("box being highlighted changes... when you get close to the right
of the screen", "capture point and where icon is differ") described a real,
visible, now-measured effect — but the mechanism is correct DPI-aware
rendering of one logical rectangle, not a coordinate bug in either the
reticle or the highlight. Nothing here is broken in the sense either ticket
assumed.

**Change.** Not a code fix — a regression test and a documentation
correction:
- Add a test asserting the relationship measured above holds:
  given two screens at different `devicePixelRatio()`, a single drag
  rect's per-screen highlight pieces must differ in physical size by
  exactly the ratio of the two screens' DPRs (within rounding), so a
  future change that "fixes" them to look the same size would be caught
  as a regression, not shipped as an improvement. Mirrors the guard-test
  precedent in `docs/TA-231.md`'s Decision section.
- Correct `TESTASSIST_BACKLOG.md`'s TA-223 entry and `docs/TA-233.md`'s own
  Problem/Scope text, which both currently describe this as an unexplained
  bug — they should describe it as confirmed-correct DPI-scaled rendering,
  with a link to this measurement.
- Leave open, as a separate product decision rather than folding it into
  this fix: whether an evidence-capture tool should visually normalize the
  highlight to look the same *physical* size across mixed-DPI screens for
  operator clarity, even though the underlying logical rectangle and the
  exported capture are both already correct. That's a UX call, not a bug
  fix, and shouldn't block closing the "is this broken" question.

**Acceptance.**
- New test passes, demonstrating the DPR-ratio relationship on a
  synthetic two-screen fixture (mirrors how TA-239's rounding test avoided
  needing real hardware).
- `TESTASSIST_BACKLOG.md` TA-223 and this file's own Problem/Scope section
  no longer describe the size difference as unexplained.
- TA-223 and TA-233 can both close as "measured, explained, not a defect"
  rather than staying open pending a fix that isn't needed.

**Not in this issue.** Whether to add a visual-normalization UX feature
