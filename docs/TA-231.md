### TA-231 — A spanning selection across screens of unequal height produces an unexplained black band

- **Phase:** 3
- **Priority:** P2
- **Suggested labels:** `ux`, `capture`, `multi-display`
- **Problem it solves:** When two displays have different *logical* heights, the
  virtual desktop is L-shaped rather than rectangular, and a rectangular
  selection spanning both necessarily covers a region that belongs to no
  screen. The export fills that region black. The fill itself is correct — no
  display is there, so there are no pixels to capture — but it arrives with no
  warning and no explanation, and the user is left deciding whether they are
  looking at a defect.

  Measured on the reference rig (laptop 1536x864 @125% at x -1536..0, external
  1920x1080 @100% at x 0..1920, tops aligned), the unmapped region is a
  1536x216 block at the bottom left. A drag from (-1400, 100) to (1800, 1000)
  yields:

  | region | extent | captured |
  |---|---|---|
  | laptop content | x -1400..0, y 100..864 | yes |
  | **unmapped**   | x -1400..0, y 864..1000 | **no display** |
  | external content | x 0..1800, y 100..1000 | yes |

  **Cropping cannot fix this.** Cutting y at 864 discards 136 rows of real
  external content; cutting x at 0 discards the laptop half entirely. The
  captured content is L-shaped, and the tightest rectangle containing an L is
  the full bounding box. Any crop that removes the band removes pixels the user
  deliberately selected.

  **Compositing the gap away is worse and is explicitly rejected.** Butting the
  two pieces together to eliminate the band would place content adjacent that is
  not adjacent on the physical desktop. For a general screenshot utility that is
  a cosmetic convenience; for an evidence-capture tool whose output goes into bug
  reports it produces a falsified artifact. The spatial relationship between
  captured regions is part of the evidence.

  So the band stays. What must change is that it stops being a surprise: the
  user should see the unmapped region *before* releasing the mouse, not discover
  it in the exported file.

  Note that constraining the cursor is not available as a remedy. Windows
  already confines the pointer to real screen area, so both corners of any drag
  are legal positions; the rectangle between them can still span unmapped space.
  Visual feedback during the drag is the only prevention that exists.

- **Scope:**
  - The overlay renders regions of `virtualGeometry()` covered by no screen
    distinctly from selectable area — hatched, or dimmed differently — so the
    unmapped region is visible while the selection is being drawn.
  - **Decide and record** whether the export fills unmapped regions with black
    or with transparency. PNG supports alpha and a transparent band drops into a
    ticket or document more cleanly, but clipboard and JPEG paths flatten it and
    some viewers render transparency as white. Decide it; do not let it default
    by inaction.
  - Update DSP-08's expected result wherever it appears. `DESKTOP_TEST_PLAN.md`'s
    CAP-16 (also labelled DSP-08) reads "no black band" — correct for *its own*
    scenario, a gap *between* two screens that `plan_capture()` already closes
    by packing them adjacently, but not achievable for a spanning drag across
    screens of unequal height, where packing one axis cannot close a real
    mismatch on the other. `MULTI_DISPLAY_MANUAL_PASS.md`'s own DSP-08 row
    ("no gap, no doubling, no vertical offset") is worded broadly enough to
    invite the same misreading — and the reference rig above has exactly this
    height mismatch. Both need the unequal-height case named as its own
    expectation rather than folded into "no gap".
- **Deliverables:**
  - The overlay change, with a test asserting unmapped regions are identified
    correctly for a non-rectangular screen union.
  - A regression test asserting that captured pieces keep their relative offsets
    — the guard against anyone later "fixing" the band by closing the gap.
  - The black-vs-transparent decision, written down whichever way it goes.
  - DSP-08's expectation corrected in `MULTI_DISPLAY_MANUAL_PASS.md` and
    `DESKTOP_TEST_PLAN.md` (not `TEST_PLAN.md`, which is the browser build's
    plan and has no DSP-08 case at all).
- **Acceptance criteria:**
  - With two screens of different logical heights connected, beginning a region
    drag shows any unmapped area visually distinct from selectable area.
  - A spanning capture's unmapped region matches the recorded decision, and the
    pass doc states that expectation rather than contradicting it.
  - A test fails if captured pieces are repositioned relative to one another.
- **Dependencies:** None blocking. Touches the same overlay geometry as the
  v1.4.0 `availableVirtualGeometry()` -> `virtualGeometry()` change (see CAP-21),
  so it is cheaper done alongside further work in that area than separately.
  Not release-blocking — 1.4.0's behaviour is correct, merely unexplained.
