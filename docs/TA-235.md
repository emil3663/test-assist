### TA-235 — CLOSED: was testing the wrong build, not a v1.4.0 defect

- **Phase:** 3
- **Priority:** ~~P1~~ Closed, 2026-09-13
- **Suggested labels:** `not-a-bug`, `multi-display` (kept for search, not active)
- **Closing verdict, 2026-09-13:** Measured. On a confirmed v1.4.0 launch, a
  corner-to-corner drag on the external exported at **1918×1080** against
  the real 1920×1080 — a 2px width shortfall, 0px height, edge pixels are
  real desktop content, not a hard-cropped bar. That's manual drag
  imprecision (0.1% of the width), not the systematic coverage boundary
  TA-232 measures on the laptop. **Quick capture reaches the whole external
  screen on the actual release build.** No fix needed; closing rather than
  reopening at P1.

  Kept below for the paper trail: this looked like a P1 blocker for most of
  today's pass, and the reason it didn't hold up is itself worth recording.
- **Status update, 2026-09-13 (superseded by the verdict above):** The
  original evidence (`test-assist-1789288651 External border quick
  capture.png`) and the restart meant to test it (`test-assist-1789293089
  restarted external quick capture.png`) were both produced against an
  **old RC3 build** (`C:\TestAssist\TestAssist-1.4.0-rc3(09092026)\
  TestAssist.exe`), not the released v1.4.0 executable — the capture saved
  into that RC's own folder, which is what surfaced the mismatch.
- **Problem it solves (as originally filed):** On the external monitor —
  1920x1080, DPR 1.0, primary — only part of the screen could be dragged
  over during quick capture; the reporter marked the rest "the lighter side
  of the screen," where no snapshot could be taken.

  **This is not TA-232.** TA-232's mechanism is a single overlay window
  taking the *primary* screen's device-pixel ratio, which under-covers a
  *secondary, scaled* screen — it explicitly does not predict any shortfall
  on the primary screen itself, which is DPR 1.0. Measuring the original
  annotated evidence found one clean, repeatable brightness boundary partway
  across the image, confirming a real edge rather than a visual artifact —
  but that evidence had already been through an edit/annotate pass, so the
  exact device-pixel position of that edge on the real 1920x1080 panel was
  never established.

  This was connected to the open question in the 2026-09-12 handover (§8):
  CAP-21 truncated the external's taskbar clock on first attempt and
  captured it in full only after an app restart. That question is now more
  likely explained the same way as this ticket's premise — a build mismatch
  rather than live geometry caching — but hasn't been re-tested against a
  confirmed-correct v1.4.0 launch either.
