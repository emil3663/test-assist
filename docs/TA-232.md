### TA-232 — The capture overlay under-covers a HiDPI secondary screen by the DPI ratio, making ~36% of it unselectable

- **Phase:** 3
- **Priority:** P1
- **Suggested labels:** `bug`, `capture`, `multi-display`, `hidpi`
- **Problem it solves:** On a mixed-DPI desktop the region-capture overlay covers
  only part of a scaled secondary screen. The uncovered margin cannot be
  selected at all, and nothing on screen indicates why — the overlay simply
  stops, and the user concludes the app ignored their drag.

  **Measured on the reference rig.** Test Assist's own About dialog reports the
  geometry:

  ```
  Screen 0: 1920x1080 at (0, 0),     DPR 1.0    (external, primary)
  Screen 1: 1536x864  at (-1920, 0), DPR 1.25   (laptop)
  ```

  With the widget on the laptop, quick capture open, and the result captured by
  Windows Print Screen (not by Test Assist, so the overlay itself is visible):

  | edge | position | brightness step |
  |---|---|---|
  | overlay right edge | **x = 1536** | 27.45 -> 39.70 |
  | overlay bottom edge | **y = 864** | 27.00 -> 39.00 |

  Above y=864 every row means exactly 27.00; below it, exactly 39.00. A step
  function, not a gradient — the dimmed region ends abruptly at 1536x864 on a
  panel that is 1920x1080 device pixels.

  1536 x 1.25 = 1920 and 864 x 1.25 = 1080. The shortfall is the DPI ratio
  exactly. **Covered area is 1,327,104 of 2,073,600 device pixels — 64%. About
  36% of the laptop screen cannot be selected.**

  **The uncovered margin includes the laptop's taskbar** (measured at y>=1020,
  well below the overlay's bottom edge at 864). CAP-21 and CAP-22 therefore
  cannot be run on the laptop at all, and an attempt there fails in a way that
  looks like the v1.4.0 `virtualGeometry()` change not working.

  **Mechanism.** The overlay is a single top-level window sized to
  `virtualGeometry()` in logical units. Qt gives one window one device-pixel
  ratio, and on a mixed-DPI desktop it takes the primary's — 1.0 here. So 1536
  logical units render as 1536 device pixels on a panel that is 1920 wide.

  **What has been ruled out, by measurement rather than argument:**

  - **Stale geometry.** The same seams appear after a full restart of the app
    (tray checked, per TA-230) with the display arrangement already settled.
    An earlier run had confounded a restart with a scaling change; this run
    separates them.
  - **A v1.4.0 regression.** At v1.3.0 the overlay used
    `primaryScreen().availableVirtualGeometry()` and had the same
    single-window-DPR exposure, so the mechanism predicts identical behaviour.
    If the overlay did not reach the secondary screen at all in v1.3.0, then
    v1.4.0 moved laptop coverage from 0% to 64%. Either way this is a
    long-standing gap that v1.4.0 partly narrowed, not something it broke.
  - **Position, screen count, or the `virtualGeometry()` change.** With both
    screens at 100% the overlay reached 3814 of the 3840-pixel virtual desktop.
    Under-coverage would have capped a drag at 3840 / 1.25 = 3072. DPI is the
    variable.

- **Scope:**
  - Make the overlay cover every screen fully at that screen's own device-pixel
    ratio. The likely shape is **one overlay window per `QScreen`** rather than
    a single window spanning the virtual desktop, since a per-screen window
    takes its own screen's DPR; alternatively, explicit DPR compensation on the
    single window. Choose and record which, with the reasoning.
  - Selection must continue to work across screens once the overlay is split,
    including a drag begun on one screen and finished on another.
  - Out of scope: any change to how captured pieces are composited or scaled.
    The exported image is correct today (DSP-05 measured 1.25x on the laptop
    against 1:1 on the external); this ticket is about what can be *selected*.
- **Deliverables:**
  - The overlay fix, with the design choice recorded.
  - A test asserting that for each connected screen the overlay's covered area
    in device pixels equals that screen's device resolution, exercised against
    a faked mixed-DPI layout so it runs on single-screen CI.
  - A test that a drag spanning two screens still yields one capture.
  - CAP-21 and CAP-22 re-run on the **laptop** once fixed; they are currently
    unrunnable there and were passed on the external only.
- **Acceptance criteria:**
  - With the laptop at 125% and the external at 100%, the overlay dims the
    laptop panel to all four edges; a Print Screen of the live overlay shows no
    interior brightness step.
  - A region covering the laptop's taskbar can be selected and captured.
  - A selection spanning both screens still produces a single image.
- **Dependencies:** Interacts with **TA-231**. If the fix is per-screen overlay
  windows, each overlay maps 1:1 onto a real display and there is no longer a
  single rectangle spanning the L-shaped virtual desktop — which would remove
  TA-231's unmapped-region case as a side effect rather than needing its own
  overlay feedback. **Decide TA-232's approach before starting TA-231**, or the
  two will be solved twice.

  Not release-blocking for anything already shipped; v1.4.0's behaviour here is
  no worse than v1.3.0's. A 1.4.1 is justified on user impact if wanted.

## Resolution (2026-09-13)

**Shape taken: option 1, one `ScreenshotOverlay` window per `QScreen`.**
`ScreenshotOverlay` is now a coordinator (`QObject`, not itself a widget)
that builds one `_OverlayWindow` per connected screen in `activate()`, each
set to that screen's own `.geometry()` rather than a shared
`virtualGeometry()`. A window set to its own screen's logical geometry
inherits that screen's own `devicePixelRatio` - the mechanism this defect
lived in - so full device-pixel coverage per screen follows from Qt's own
per-monitor-DPI-aware model rather than needing to be computed or
compensated for by hand.

**Option 2 (explicit DPR compensation on one window) was not taken.** A
single window still has exactly one DPR no matter what geometry it is
given, so covering a HiDPI screen fully would have meant manually painting
device-pixel-correct content inside logical-pixel-sized widget space -
more code, and a second, bespoke coordinate system to keep in sync with
Qt's own, for a problem Qt already solves natively once each screen has its
own window. Nothing measured suggested option 2 would have been cheaper or
safer; it was never prototyped.

**What the port needed beyond window construction**, per this issue's own
"hard part" list:

- The drag is tracked once, at the coordinator, in global (virtual-desktop)
  coordinates - not per window. Whichever `_OverlayWindow` receives
  `mousePressEvent` calls `grabMouse()` on itself, so Qt keeps delivering
  every subsequent move/release to that same window even once the cursor
  leaves its own screen. The coordinator recomputes the shared selection
  rect on every move and pushes each window its own local share of it
  (`_OverlayWindow.show_selection()`), so a window that never receives a
  mouse event of its own still redraws correctly. Covered by
  `test_a_drag_crossing_screens_updates_both_windows_and_yields_one_capture`
  in `python/tests/test_capture.py`.
- `_covered_region()` is gone rather than ported: each window's rect now
  *is* one real screen in full, so there is no gap within a window's own
  bounds left to exclude from its dim. See the TA-231 decision below for
  what this removes.
- The TA-223 debug logging (`capture.py`, `mouseMoveEvent`) still fires on
  every move of a drag, from the coordinator's single `mouseMoveEvent`,
  regardless of which window's `grabMouse()` is actually receiving the
  underlying event - unchanged in content, just no longer duplicated per
  window.
- `_grab()` and everything in `screen_geometry.py` (`plan_capture`,
  `composite_ratio`, `to_device_rect`) are untouched, as scoped - the
  grab/composite path was already correct; this issue was only ever about
  what could be *selected*.
- `_virtual_origin` and `_to_local()` are gone rather than ported forward.
  They existed to translate a global point into one shared window's local
  coordinates, and to survive the widget being hidden (CAP-14b's original
  concern - a hidden window is not guaranteed to keep reporting the
  geometry it had while shown). Each `_OverlayWindow` now stores
  `screen_geometry` as a plain Python attribute set once at construction,
  never re-read from Qt, so the same robustness holds structurally instead
  of needing a dedicated workaround.

**New pure function, in `capture.py` (not `screen_geometry.py`, which this
issue leaves unchanged): `overlay_device_coverage(screen_geometries,
screen_ratios)`.** Takes literal `QRect`/`float` values, not live `QScreen`
objects, and returns the device-pixel size each per-screen window ends up
covering - asserted against the reference rig's own numbers (1536x864 @1.25,
1920x1080 @1.0) in `python/tests/test_capture.py`, which also runs offscreen
on single-screen CI. This is the "window-level test" this issue's own Test
section asked for, plus window-construction and cross-screen-drag tests
that exercise `ScreenshotOverlay.activate()` and the real per-window mouse
path end to end.

**Test suite:** `python/tests/test_capture.py` is new. `test_screen_geometry.py`
is unchanged, as scoped. `test_functional.py`'s existing overlay cases
(CAP-01/02/03/10/11/13/14/14b/15/21, DSP-04/08, TA-223/225 logging) were
updated where they depended on the removed single-window API
(`overlay.geometry()`, `_virtual_origin`, `_to_local()`, `_covered_region()`)
and left as-is everywhere else; all pass, along with
`test_regressions.py` (aside from the pre-existing, environment-specific
`TA-211` real-Win32-hotkey-registration failures, unrelated to this change
and present on `main` before it).

See `docs/TA-231.md` for the recorded decision on the unmapped-region case
this same port affects.
